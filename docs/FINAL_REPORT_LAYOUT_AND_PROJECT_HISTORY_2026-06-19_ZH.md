## 1. 总体判断

Holo 的最终报告应写成“智能体运行框架从原型到成熟检查点的演化”。金融 benchmark 是验证场景，系统设计和迭代过程才是报告主线。

更准确的项目主线是：

```text
长期记忆与自迭代原型
  -> 工具调用、运行日志和可视化工作流
  -> Kernel v3 的宿主程序控制型智能体运行框架
  -> 金融任务包成为高压评测场景
  -> v3 暴露自研语义闸门和信息槽绑定的泛化瓶颈
  -> 参考成熟项目后，Kernel v4 重写为通用单智能体循环
  -> 用 FinanceBench 在线严格评测验证系统能力和边界
```

这条主线更符合课程要求中的“从 AI 工具使用者到科研系统构建者”。它能说明：

- 为什么公开财报研究值得用智能体系统解决；
- 系统相对于简单 API 调用多出了哪些执行、验证和记录能力；
- 项目如何经历设计、失败、纠偏和实验；
- 最终结果既有能力数据，也有边界分析。

## 4. v3 与 v4 的诚实评估

### 4.1 v3 的真实价值

v3 的价值不应被否定。它完成了很多后续 v4 仍然继承的基础：

- 宿主程序掌握执行边界的循环不变量；
- 日志和可观察运行过程；
- 检索工具台；
- SEC/EDGAR/companyfacts 路线；
- 金融事实账本、主张账本、信息槽和公式轨迹；
- 计算器和数值核验器；
- 演示看板和运行过程可视化；
- 在线评测才能作为能力证据的纪律；
- FinanceBench/FAB/FinQA 题型分析。

v3 的 demo 和 PPT 很适合说明项目的连续建设过程：它先形成可观察的运行框架，再进入金融任务验证。

### 4.2 v3 的主要问题

v3 后期的问题也必须诚实写：

- 语义闸门太多，FactLedger/SlotFrame/slot_bind 容易成为模型行动的阻塞点。
- 部分“补槽”和“公式脚手架”接近规则系统，可能削弱泛化性。
- LangGraph 虽开始接入，但 Holo 自研控制流仍较重。
- 工具结果和证据对象的生命周期不够成熟，模型有时拿不到已经获得的证据。
- 单题成本高，失败后容易继续加局部补丁。

这些问题构成 v4 重写的必要性。

### 4.3 v4 的成熟点

v4 的成熟体现在边界更干净：

- 单智能体循环回到通用工具调用机制；
- 模型选择工具，host 执行和记录；
- 流式工具执行器支持模型在输出过程中发起工具；
- 工具发现和工具台负责暴露能力，模型仍然决定使用方式；
- 证据对象生命周期解决大文档和大工具结果无法全部进入上下文的问题；
- 无答案任务包和评分入口形成严格评测路径；
- 计算和最终回答检查点承担通用防护作用，不能被写成答案表。

### 4.4 v4 仍然不足

v4 当前仍有明确边界：

- 剩余 54 题严格评测结果为 `42/54 = 77.78%`，这不能写成完整 100 题干净测试。
- 主要失败来自数值误差，说明财务口径、单位、符号、期间和最终答案完整性仍需加强。
- offset `121` 的空最终答案说明收尾阶段仍有可靠性风险。
- offset `97` 和 `143` 说明复杂题可以做出来，但轮数、工具调用和总 token 成本仍很高。
- 目前仍是单智能体，尚未实现多候选分支、多路线竞争和独立审计。

报告中应把这些写成“系统边界和未来工作”，直接说明当前版本的未完成部分。

## 9. 最终报告的叙事风险

### 风险 1：早期 biomimetic 叙事过重

早期 stage 里有很多仿生和意识相关术语。最终报告应把它们处理为早期工程探索，避免把这些术语写成核心科学主张。更稳妥写法：

```text
早期探索主要帮助我们形成了对长期记忆、状态观测、运行日志和动态反馈的工程认识。
最终系统采用更可审计的智能体运行框架术语来表达这些能力。
```

### 风险 2：v3 高分和 v4 strict 结果混淆

